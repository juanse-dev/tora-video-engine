# AUDIO-005 — Browser and CLI rendering with audio

Status: implemented

Depends on: AUDIO-002, AUDIO-003, and AUDIO-004 for the bundled-audio store (`src/web/audio/bundledAudio.ts`) that browser readiness and preparation read; the CLI tasks do not need it. Read [README](./README.md) and [ASSET-004](../assets/ASSET-004-preview-and-browser-rendering.md) / [ASSET-005](../assets/ASSET-005-cli-local-assets.md) first.

## Goal

`Render MP4` in the browser and `npm run video` produce H.264 + AAC-LC 48 kHz stereo MP4s with the plan's mix whenever the Story has audio (AINV-9; 128 kb/s is requested on both paths and holds for the CLI and for native browser AAC, the WASM AAC fallback may write less, D-13), and exactly the v0.3 video-only output when it does not (AINV-6). No render starts with an audio source that has not been preflighted (AINV-8).

## Browser

### Readiness (before the Render button is enabled)

- `collectStoryLocalAssetUsages` includes `local:audio:` refs (AUDIO-003), so every ref is resolved, locked and verified through one list. **Budgets never see the unfiltered list.** Readiness splits it by category first (`splitUsagesByCategory`, AUDIO-003): the `pose`/`background` usages, with only `kind: "image"` metadata, go to `evaluateLocalAssetBudget` (unchanged limits: refs, bytes, the 200 MP pixel total); the `audio` usages, with only `kind: "audio"` metadata, go to `evaluateAudioBudget` (`MAX_BROWSER_STORY_AUDIO_REFS`, `MAX_BROWSER_STORY_AUDIO_BYTES`, its own messages `This Story uses more than 64 audio files.` / `This Story's audio is larger than 256 MiB.`). Each budget counts its own refs and bytes. `evaluateLocalAssetBudget` itself becomes fail-closed: a usage whose metadata is not `kind: "image"` (or lacks finite `width`/`height`) returns a failure instead of adding `NaN` to the pixel total; `evaluateAudioBudget` does the same for non-audio metadata.
- **Two different frame checks, on purpose.** (a) The **acceptance** policy (implemented in AUDIO-001; `evaluateBrowserStoryPolicy`, which gates every candidate before it becomes active, including the stored project at start-up, before My assets has opened) must not depend on asynchronous asset state, or a stored Story could be rejected into a recovery snapshot just because durations had not loaded yet. It counts each `auto` scene at its **lower bound** `AUTO_DURATION_MIN_FRAMES = ceil(AUTO_DURATION_PADDING_SECONDS × fps) + 1` (16 at 30 FPS; a voice is `> 0` s) and fixed scenes as today, so it never rejects a Story that could fit. (b) **Render readiness** evaluates `MAX_BROWSER_TOTAL_FRAMES` on the exact `compileTimeline(story, fps, audioDurations).durationInFrames` and blocks with `This Story is longer than 300 s with its voices (N s).` A `fallback` scene (voice not available) already blocks render through the `missing-audio` or `pending-audio` issue. The Player and timeline UI handle any length (voices are capped at 300 s each, so the worst case is bounded).
- **Readiness before the click never uses the render's source map** (that map is only built inside the transaction, after the click; requiring it here would keep every bundled Story blocked forever). Readiness compiles the plan with a **readiness source state**: a local audio ref is `ready` when the page's local-asset state has it verified and its duration is known, `pending` while it resolves, `missing` when absent; a bundled id comes from AUDIO-004's `useBundledAudioStates()`: `ready` → ready, `loading`/`retrying`/`fetch-failed` → pending, `unusable` → missing. Render is blocked while that plan has `missing-audio` **or** `pending-audio` (AINV-5: not-yet-ready audio never renders), with `Audio is still loading.` (`Audio could not be loaded. Retry it in the editor.` for `fetch-failed`) or `Audio file <id> cannot be used for rendering.` (`unusable`). Because readiness takes the store snapshot and the local-asset state as inputs, the button enables by itself when the last pending id becomes ready. `voice-cut`, `fades-scaled` and clipping are warnings only.
- Capability (D-13): `checkBrowserRenderCapability` calls `canRenderMediaOnWeb` with `muted: !storyHasAudio(story)`; with audio it requests `audioCodec: "aac"` and, if AAC is not natively encodable, awaits the web-renderer's WASM AAC registration before deciding (`canRenderMediaOnWeb` performs that registration itself when `audioCodec: "aac"` and `audioBitrate: OUTPUT_AUDIO_BITRATE` are requested and no native encoder exists; the WASM encoder is a valid path, D-13). If AAC is still unavailable: blocked with `This browser cannot encode audio. Use the local CLI: npm run video -- <story.yaml>`. The capability result is cached per `storyHasAudio` value, so a silent Story never pays for the audio probe. If the probe throws, the failure is cached too (one probe per value for the page session) and the banner shows the same unsupported message the click shows; when the cause is the lazily loaded WASM AAC chunk failing to load (a stale tab after a deploy, a network failure: `Failed to fetch dynamically imported module` and its siblings), the message is `Browser render could not load its audio encoder. Reload the page to try again. Preview, YAML export, and the local CLI remain available.` instead of the technical text, because only a reload can retry a failed dynamic import.

### Transaction

- `prepareLocalAssets` (ASSET-004) prepares audio refs exactly like images: verified payload → object URL, held by the render lease until the post-render cleanup; a change between preparation and render returns `assets-changed`. **Bundled audio** is taken from AUDIO-004's store inside the transaction: each referenced id must be `ready`, and its `blob` (already inspected, fully decoded and truncation-checked in this page session, which satisfies AINV-8 for exactly these bytes) gets a render-owned object URL in the frozen `audioSources` under the bundled id, revoked with the lease; the renderer never re-fetches `staticFile`. The composition's `audioSources` are `buildAudioSourceMap(story, preparedSources, frozenBundled)` (AUDIO-002): the lease-owned local audio URLs from `prepareLocalAssets` plus the frozen bundled URLs. The transaction then **re-checks the frozen map**: it compiles the plan with `bundledAudioPolicy: "explicit"` (AUDIO-002) and those `audioSources`, and returns `assets-changed` without touching OPFS if any `pending-audio` or `missing-audio` remains (e.g. an id turned `unusable` between the click and preparation).
- **Preflight** (AINV-8), inside the same preparation and before OPFS cleanup, for every audio source the plan will use (bundled and local), on the exact bytes the render will read (bundled: the store's verified `blob`, so its decode in this session is the store's; local: the verified payload):
  1. `inspectAudio` succeeds and matches the expected duration within 1 ms (for local refs this is the integrity check already performed; for bundled ones it is new);
  2. **a full decode in this page session** (for bundled audio, of the same Blob the render reads through its object URL): `decodeAudioPeaks` (AUDIO-003) completes without error and its decoded length passes the truncation rule (D-9). Import-time decoding does not count: after a reload, bytes whose metadata still parses could fail to decode, and only a decode proves the renderer will not stall on them.

  Local results are cached per digest for the page session in a `AudioDecodeCache` (bundled ids are decoded once by AUDIO-004's store, whose `ready` state is the cached result) that follows the integrity cache's rules (D-8 of ASSET-004 R14: one decode at a time page-wide, in-flight sharing per digest, invalidation by a library change wins over an in-flight result, abort only stops waiting). A Story's first render therefore pays at most one decode per distinct source (S-7: ~1 s for a 300 s MP3), later renders none. The preflight honours the render's abort signal. Failure → `{kind: "failure"}` with `Audio file <label> cannot be used for rendering.` and no render. `delayRenderTimeoutInMilliseconds` is set to `30_000` for renders with audio so a source that still stalls fails with a clear timeout instead of hanging.
- `renderMediaOnWeb`: `muted: !storyHasAudio(story)`; with audio, `audioCodec: "aac"`, `audioBitrate: OUTPUT_AUDIO_BITRATE`; `inputProps` include `audioDurations` and the local sources (images + audio). Cancel keeps settling `idle` (v0.3.1).
- Post-render check (new: `src/web/renderedMp4Check.ts`; the product had no such check, the "existing download check" was only the golden test's ffprobe assertions). It runs on the rendered Blob before the download, only for a Story with audio: exactly one audio track whose codec string is `mp4a.40.2` (AAC-LC; HE-AAC `mp4a.40.5`/`mp4a.40.29` fails), 48 kHz, 2 channels, an average bitrate above 0 (audio packet bytes × 8 / audio duration, from mediabunny packet stats), and an audio duration within `1 / fps` + 60 ms of the video track (both durations must be finite and above 0, and every comparison fails closed: a NaN or infinite number read from the file rejects the MP4); the video track must be H.264, 1080×1920, 30 FPS with frame count = plan `T`. There is **no bitrate range** in the product check: the WASM AAC encoder ignores the requested 128 kb/s (measured 67–89 kb/s) and D-13 accepts it. The 115.2–140.8 kb/s range (128 kb/s ±10%) is asserted only by the tests of the native-AAC path and of the CLI. Without audio nothing is checked (AINV-6).

## CLI

- `renderStory` builds `audioDurations` with `storyAudioDurations(story, localDurations)` (AUDIO-001, the same entry point as the browser), where `localDurations` come from `inspectAudio` on the matched `local-assets/audio/` files (AINV-3), and passes it in `inputProps` together with the staged audio sources (`{kind: "static", path}` under `__local-assets/`).
- **Before spawning Remotion**, the CLI compiles the timeline and the plan with the same map and refuses to render while `plan.issues` contains `missing-audio`, `pending-audio` (cannot happen with staged sources; treated as an internal error) or `story-too-long-for-audio`, for **every** source kind: a missing local file, and a bundled id whose catalog `file` is null (the placeholder music ids) or whose file is absent from `public/audio/`. The error lists each with its role (`music`, `scene 3 sfx`, `scene 3 voice`), using the image "missing local assets" wording for local refs and `Bundled audio <id> is not available in this build.` for bundled ones. AINV-5: the CLI never renders with an audio source silently omitted.
- **Bundled audio is staged too.** Like local files (snapshot-on-match), every bundled file the plan uses is copied from `public/audio/` into the command's private staging directory **before** any inspection, and the props' `audioSources` are `buildAudioSourceMap(story, stagedSources, stagedBundled)` (AUDIO-002): staged `local-assets/audio/` copies for local refs and the staged copy for each bundled id (`{kind: "static", path}` under `__local-assets/`) with `bundledAudioPolicy: "explicit"` (AUDIO-002). Remotion therefore reads the snapshot, never `public/audio/` directly, and a change to `public/audio/` after staging cannot reach the render.
- **CLI decode preflight** (AINV-8), after staging and before spawning Remotion, for every audio source the plan uses (staged local copies and staged bundled copies), on the exact files the render will read. First, metadata: `inspectAudio` on each file must pass every AINV-7 rule (one audio track, no video track, accepted codec, duration and format bounds; staged local copies were already inspected when matched, and are re-inspected here since it is cheap), and a bundled file's `durationSeconds` must equal its catalog value within 1 ms, else `Bundled audio <id> does not match the catalog.`. Only then the decode: `scripts/audioPreflight.ts` runs the ffmpeg binary that ships with Remotion (the compositor-package lookup moves from `tests/helpers/ffmpeg.mjs` to `scripts/ffmpegBinary.mjs` with a hand-written `ffmpegBinary.d.mts`, plain JavaScript because Playwright's loader cannot import a `.ts` file from the `.mjs` test helpers, which re-export it) as `ffmpeg -v error -nostdin -i file:<path> -map 0:a:0 -ac 1 -ar 48000 -t 301 -c:a pcm_s16le -f wav -` (the repository ffmpeg has no raw `f32le`/`s16le` muxer) with a 60 s timeout, counting the bytes after the WAV header without buffering them: `decodedSeconds = bytes / (2 × 48_000)`, and stopping the child once its decoded output exceeds the 302 s byte bound (301 s plus one second of slack; the failure says `ffmpeg decoded more than 301 s of audio`, and `-t 301` already caps what the real ffmpeg writes). The child is attached to the command's interrupt guard, so Ctrl+C and SIGTERM kill it. There is no `-xerror`: a file the browser import accepts is accepted here too. A non-zero exit, a timeout, output past the bound, or `!isDecodeComplete(decodedSeconds, durationSeconds)` (the D-9 truncation rule, so zero decoded bytes always fails; `durationSeconds` = the same `inspectAudio` value used for the timeline, AINV-3) refuses the render with `Audio file <name> cannot be used for rendering.` and the role list. Sources are checked one at a time; a 300 s MP3 decodes in about a second. Node's lack of WebCodecs does not matter here: the decoder is ffmpeg, the same family Remotion's own audio extraction uses.
- `npm run video` does not call `renderMedia`: `scripts/renderStory.ts` runs the `@remotion/cli` child process with the arguments from `scripts/renderSupport.ts::buildRenderArgs`. That function gains an options parameter, `buildRenderArgs(outputPath, propsPath, publicDir?, {hasAudio})`. With `hasAudio: false` the argument list is **byte-for-byte the v0.3 list** (AINV-6; no `--muted`, no audio flags). With `hasAudio: true` it appends `--audio-codec=aac`, `--audio-bitrate=128k` and `--enforce-audio-track` (D-14; flags verified to exist in `@remotion/renderer` 4.0.529 options `audio-codec`, `audio-bitrate`, `enforce-audio-track`). The last one is what keeps AINV-9 true when the mix is inaudible (for example an `sfx` at `volume: 0`): without it Remotion drops the silent audio and the CLI would write a video-only file while the browser writes a silent AAC track; with it both write exactly one AAC-LC track. Durations reach the composition through the props file (`--props`), which now also contains `audioDurations` next to `story` and the staged sources; `calculateMetadata` (AUDIO-001) reads them.
- The interrupt guard (#37) already removes the staging directory; audio files are staged into the same directory, so no new cleanup path exists. A test asserts it.

## Done when

## Implementation notes

- The browser has no render without the bundled-audio store of AUDIO-004: readiness reads `useBundledAudioStates()`; the preparation reads `getBundledAudioStates()` once the render lock is granted and before OPFS is touched.
- The CLI stages the bundled files under `__local-assets/bundled/<id>.<ext>`; `scripts/audioRender.ts` orchestrates staging, metadata, the plan check and the decode preflight. The shared plan of a frozen source map is `compileFrozenAudioPlan` (`src/audio/readiness.ts`).
- `disallowFallbackToHtml5Audio` is `true` exactly while Remotion renders (`useRemotionEnvironment().isRendering`: the CLI and the browser renderer, which never falls back anyway); the Player and Studio keep the default.
- The repository ffprobe prints the AAC profile as `1` (LC); the tests accept `LC` or `1`.
- The CLI decode preflight fails only on a non-zero exit, on a decode that produced nothing, on output past the 302 s byte bound (reported as `more than 301 s`), or on the D-9 truncation rule; it does not use `-xerror`, so a file the browser import accepts (a benign trailing frame error) is accepted by the CLI too. It also passes `-nostdin`, a `file:`-prefixed path and `-t 301`, and the ffmpeg child is attached to the command's interrupt guard (Ctrl+C or SIGTERM kills it).
- `AudioDecodeCache` gives every decode a 30 s timeout and an abort signal: a decode that never settles fails (and the queue moves on) instead of blocking every later render.
- Readiness reads the duration of a local voice from its verified payload (the one the render uses), so a failed read of the page's own duration map can never leave the Story at "Audio is still loading."
- An audio Story over the audio budget (more than 64 distinct local audio files or 256 MiB) is `over-budget` exactly like an image Story over its budget: the Player and the audio timeline give way to the message (ASSET-004).
- `disallowFallbackToHtml5Audio` makes a Remotion-Chrome decode failure of a file that passed the ffmpeg preflight a bare `Remotion render failed`; verified with Remotion's bundled Chrome on Windows for an M4A voice, and the decode-failure path is exercised on Linux by CI's `test:cli-e2e` with the system Chrome for WAV voices only: MP3, M4A and Opus voices were verified under system Chrome on Windows, not on Linux CI.
- CI: `.github/workflows/ci.yml` `timeout-minutes` goes from 15 to 25. Measured on the development machine: the new system-Chrome spec file took about 32 s in total when measured on Windows (estimated at 42 s; 10 tests, one worker) and the new CLI renders add about 45 s (`test:cli-e2e` goes from about 14 s to about 60 s); a hosted runner is typically 2 to 3 times slower, so about 3 to 4 more minutes in the one `verify` job.
- A `Checking audio…` status shows in the render banner while the sources are inspected and decoded.
- The normative text above is current: the CLI preflight decodes to WAV on stdout (no `f32le` muxer in the repository ffmpeg), the lookup is `scripts/ffmpegBinary.mjs` + `.d.mts`, and the post-render check is the new `src/web/renderedMp4Check.ts` (Stories with audio only). Measured with system Chrome 155 on Windows: AAC-LC is natively encodable at 48 kHz stereo 128 kb/s (output 128 kb/s). With native AAC forced off, the web renderer registers its WASM AAC encoder (D-13): WASM AAC ignores the requested bitrate (measured 67-89 kb/s); accepted. That render succeeds and passes the check.
- Test placement: the new unit tests live in `tests/audio-render-readiness.test.mjs`, `audio-capability.test.mjs`, `audio-readiness.test.mjs`, `audio-duration-parity.test.mjs`, `audio-seed-fixtures.test.mjs`, `audio-render-preparation.test.mjs`, `audio-decode-cache.test.mjs`, `rendered-mp4-check.test.mjs`, `cli-audio-render.test.mjs`, `audio-preflight.test.mjs`, `audio-envelope.test.mjs`, `app-audio-render.test.mjs`; the system-Chrome specs in `tests/browser/audio-rendering.spec.mjs`.
